### Bug: C: subdirectories returned garbage / Erc 668 / Erc 224
Symptoms, in order, while trying disk layouts:
1. 16×63 geometry, partition at LBA 63: `dir C:\` worked, but `dir C:\MSAMPLES` printed file data (ASM source)
   as directory entries, then Erc 668 (`ErcBadCmd`, IDE abort).
2. 16×17 geometry, partition at LBA 17: `dir C:\` was empty, and subdirectories gave Erc 224 (`ErcNoMatch`).

Diagnosis with QEMU tracing (`run.sh -trace ide_ioport_write -trace ide_sector_read -D /tmp/ide.log`):
- `dir C:\` read **sector 491**, but the root is at **474** (17 + 1 + 2×228). The CHS registers written were
  C=1 H=12 S=16, which is LBA 474 converted with **15 heads**, while the disk (and QEMU) has 16.
- The driver's `SET_PARAMS` (0x91) wrote Device/Head `0xAE`, i.e. 15 heads. With a 15-head disk it wrote `0xAD`
  (14 heads), so the driver is always one head short.
- Cause: `OSSOURCE/FSYS.C:579` `PDrvs[d].nHeads = partab[i].HeadEnd;`. HeadEnd is the highest head *index*
  (heads − 1), not the count. The source's `SetDriveGeometry` later overrides it with `ReadCMOS(0x1d)`
  ("fix for 3 gig hard disk"), but **the shipped `MMSYS/MMURTL.RUN` doesn't have that override**. This is
  another case of the binary not matching the source.
- Second factor: `HARDIDE.C` starts with a hardcoded 16×17 geometry, and `read_PE → GetBSInfo` reads the partition
  boot sector with it before learning the real geometry. Disks with 63 sectors/track break that first read.

Fix (tools only, original files untouched): `tools/boot32/mkhdd.sh`
- Classic geometry 16 heads × 17 sectors × 216 cylinders (~28.7 MB), with the partition at LBA 17 (CHS 0/1/1).
- MBR HeadEnd is written as `heads` (16) instead of 15, to match what this binary expects. mtools and QEMU only
  use the LBA fields.
- `run.sh` passes the same geometry to QEMU (`cyls=216,heads=16,secs=17`).

Result: Monitor shows `C: Heads 16, Sec/Trk 17, ... FAT16`. `dir C:\` lists `MMURTL` (label), `MMSYS` and
`MSAMPLES`, and `dir C:\MSAMPLES` lists all sample directories (paged with "ESC to cancel").

Note for the port: the 64-bit FS/IDE code must take geometry from the drive (IDENTIFY) or use LBA, never from
partition-table CHS fields.

## M1 — Hello, long mode (branch `m1-longmode-boot`)

Resumed after the pause. Goal: GRUB boots a 64-bit DOORS kernel that prints a banner.

### What was built (`port64/`)
- `boot/boot.asm`:
  - Multiboot2 header and 32-bit `_start`, with checks for the MB2 magic, CPUID and long mode. On error it
    prints `DOORS boot error: M/C/L` on VGA.
  - Boot page tables: the first 1 GiB in 2 MiB pages, mapped at 0 (identity) and at `0xFFFFFFFF80000000`
    (PML4[511] → PDPT[510]).
  - PAE, EFER.LME and PG on, then a minimal 64-bit GDT and a far jump to 64-bit code.
  - Loads the higher-half kernel stack (16 KB, `.bss`) and calls `kmain(magic, mbi)`.
- `linker.ld`: `.boot*` at physical 1 MiB; the rest at `KERNEL_VMA + phys`, loaded right after `.boot` (AT()).
- `drivers/serial.c` (COM1 115200 8N1), `drivers/vga.c` (80×25 TTY, scrolling, hardware cursor),
  `kernel/console.c` (`kprintf` to both, `panic`), `kernel/multiboot2.c` (loader name, cmdline, memory map),
  `kernel/main.c` (banner, boot info, CPU state, `DOORS: M1 OK`, isa-debug-exit when cmdline has `test`).
- `include/doors/`: `types.h` (MMURTL-style U8…S64, `erc_t`, `PHYS_TO_VIRT`), `x86.h`, `console.h`,
  `multiboot2.h`.
- `Makefile`: `make`, `run`, `debug`, `test`, `clean`, and `QEMU_EXTRA`. `grub/grub.cfg` takes the kernel
  cmdline from a template (the test ISO passes `test`).

### Bugs hit while building
- I first declared `kernel_stack_top` in C as a pointer variable, while `boot.asm` used it as a label (`mov
  rsp, kernel_stack_top` would load the variable's address). Fixed by defining the stack in `boot.asm`'s `.bss`.

### Results
- Compiles cleanly with `-Wall -Wextra -Werror`. `grub-file --is-x86-multiboot2` passes. The ELF has `.boot` at
  0x100000 and `.text` at 0xFFFFFFFF80106000 (phys 0x106000); the kernel is 28 KB.
- `make test`: **TEST PASS: DOORS: M1 OK** (QEMU exit 33). Serial log shows GRUB 2.06, 6 memory-map entries,
  255 MB usable (QEMU -m 256M), `CR0=80000011 CR3=101000 CR4=20 EFER=500` (LME+LMA).
- `make run` in a WSLg window shows the same output (read back with `qscreen.py --sock /tmp/doors.mon`).
- `-d int,cpu_reset`: no exceptions or interrupts logged during boot (the 2 resets are QEMU power-on).
  That one-off run exited with status 0 instead of 33; `make test` gets 33 consistently and is the
  authoritative check.

### Decisions
- Toolchain: Ubuntu's own x86-64 `gcc` with `-ffreestanding -mcmodel=kernel -mno-red-zone
  -mgeneral-regs-only` instead of a separate `x86_64-elf-gcc` cross compiler. It works for a freestanding ELF
  kernel and saves building a toolchain. Revisit if libgcc or host-header issues appear.
- Header directory is `include/doors/` (was `include/mmurtl/` in the plan).
- The full 64-bit GDT (user segments + TSS) moves to M2, where the TSS is needed for IST stacks.
