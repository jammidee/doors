## ROADMAP.md
- User request: a roadmap for DOORS to become stable like other operating systems.
- New `ROADMAP.md` defines "stable" as measurable goals: 72 h soak with no panic, 24 h fuzzing, no data loss on power cuts on real disks, programs unable to hurt the system, 5 real PCs + 3 hypervisors, predictable releases.
- It records where 1.1.0 stands and gives 8 stages, each step with a done-when test: 1 storage (htree, deep extents, csum journals, corrupt-image fuzzing, FAT dirty flag, ext4 system disk), 2 testing (CI, syscall fuzzer, soak, debug aids, static analysis, coverage, crash reports), 3 core hardening (kmalloc and growable tables, exhaustion paths, per-job limits, service timeouts/restart, watchdog), 4 real hardware (ACPI, APIC/HPET, PCI, AHCI, NVMe, USB, UEFI, a hardware lab = 2.0), 5 SMP, 6 security, 7 usable system (malloc/libc, CLI wildcards/redirection, debugger, installer, networking, self-hosting), 8 release engineering.
- Order: storage and testing first, then hardening, then hardware. Linked from PLAN.md and CLAUDE.md.

## M8b part 2 finished: htree directory writes (1.2.0)
- On "continue" I recapped where we stopped (G:\TWO had 700 entries, expected 720), then debugged.
- Counts after each phase: after the creates ONE 400 / TWO 800, after the deletes TWO 700. Both right.
  - The 20 moves lost their entries.
  - **Cause, a test bug:** the destination path was built by overwriting `to[4..6]`, but "ONE" sits at `to[3..5]` in `G:\ONE\...`. The files were renamed to `G:\OTWOnew…` in the root of G:.
  - Fixed in kernel/selftest.c test_htree. e4_rename itself was correct.

- check_disk still reported 387/754 names. `debugfs ls -p` lists unused entries too (inode 0).
  - A deleted first entry of a block keeps its name with inode 0, as on Linux, and there are also the nameless empty records of index blocks.
  - check_disk now skips inode-0 lines. tools/powercut.py ls_pc had the same latent bug (it would have reported a deleted file as present) and was fixed the same way.
